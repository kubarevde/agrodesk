# Единая цепочка учёта урожая (ADR + UX)

Связанные документы: [shipments.md](./shipments.md), [shipment-requests.md](./shipment-requests.md).

## Ментальная модель

```
Культура (словарь)
    → Поле (crop_code)
    → Сбор («Собрать урожай») → приход harvest‑SKU на склад
    → Заявка на отгрузку (kind=harvest) → расход склада
    → Запись «Отгрузки урожая» (shipments, опц. ссылка на заявку) → KPI / прогноз
```

Один физический факт **не** пишется дважды как «два независимых учёта»:

| Факт | Где правда |
|------|------------|
| Остаток зерна на складе | `inventory_operations` / `inventory_items` |
| Наряд «отгрузить покупателю» | `shipment_requests` → при complete только склад |
| Выручка / кг культуры для KPI | только `shipments` (управленческий документ) |

`shipments.shipment_request_id` — **связь**, а не второе списание.

---

## 1. Культура в словаре

1. **Настройки → Культуры** (`org_dictionaries`, `type=crop`).
2. У каждой культуры есть стабильный **`code`** (например `wheat`) и отображаемое **имя**.
3. Код используют поля, harvest‑позиции склада и (предпочтительно) отгрузки урожая.

Без культуры в словаре нельзя корректно завести поле с `crop_code` и harvest‑SKU.

## 2. Культура на поле

1. Раздел **Поля** → создать / редактировать поле.
2. Выберите культуру из словаря — сохраняются `crop_type` (имя) и `crop_code` (код).
3. Для сбора урожая с поля **нужен** заполненный `crop_code`.

## 3. Harvest‑позиция на складе

1. **Склад** → добавить позицию, категория **«Урожай (на складе)»** (`harvest`).
2. **Культура обязательна** (`crop_code` из того же словаря).
3. Ед. изм. по умолчанию кг (можно изменить).
4. Это складской товар, **не** KPI по культурам.

## 4. «Собрать урожай» с поля

1. На карточке поля — кнопка **«Собрать урожай»**.
2. Нужны: культура у поля + хотя бы одна активная harvest‑позиция с тем же `crop_code`.
3. Каждый сбор = новый **приход** (`purpose=harvest_income`, `field_id`) — остаток harvest‑SKU растёт.
4. В карточке позиции на складе видны сборы по полям и история «Сбор с поля …».
5. **Не** создаёт запись в «Отгрузках урожая».

## 5. Продажа через заявку (со склада)

1. Со склада / из заявки: заявка на harvest‑SKU (тот же механизм, что у топлива).
2. `kind=harvest` выставляется автоматически из категории.
3. **Complete** → расход склада (`purpose=shipment_request`). KPI урожая **не** меняется.
4. Затем менеджер в **«Отгрузки урожая»** создаёт запись и **рекомендуется** привязать выполненную harvest‑заявку (поле «Связь с заявкой»).
5. KPI/прогноз читают только `shipments`.

Рекомендуемый порядок против «двойной продажи» по смыслу: сначала заявка (склад), затем ship с привязкой. Ship без заявки допустим осознанно (продажа мимо склада) — система не блокирует, только подсказывает.

## 6. Продажа «мимо склада»

Только запись в `shipments` без заявки и без складского расхода — осознанный управленческий кейс.

---

## Источники правды (не смешивать)

| Метрика | Единственный источник |
|---------|------------------------|
| Урожай в кг / выручка / прогноз | `shipments` |
| Остатки и движения (в т.ч. зерно на складе) | `inventory_operations` |
| Операционный наряд «отгрузить» | `shipment_requests` → complete → склад |

## Тип заявки `kind`

| `kind` | Когда | При complete |
|--------|--------|--------------|
| `inventory` | обычные ТМЦ | `inventory_operations` expense |
| `harvest` | категория `harvest` | то же; **не** создаёт `shipments` |

## Связка `shipments.shipment_request_id`

- Только `kind=harvest` и `status=done`.
- Управленческая ссылка; расхождения кг/цены логируются, не блокируют.
- Не дублирует складское списание.

## Что сознательно не делаем

- Не пересчитываем `shipments` ↔ `inventory_operations` 1:1.
- Не требуем вести весь урожай только на складе.
- Не вводим отдельный тип «заявка на урожай» — это та же заявка.
