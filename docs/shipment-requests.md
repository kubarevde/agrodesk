# Заявки на отгрузку ТМЦ / урожая-как-товара

Модуль оформляет **намерение** отгрузить позицию склада покупателю.
Тип заявки `kind`:

| kind | Смысл | При complete |
|------|--------|--------------|
| `inventory` | обычные ТМЦ | `inventory_operations` |
| `harvest` | категория склада `harvest` | тоже `inventory_operations` (остаток), **без** `shipments` |

См. [harvest-tmc-link.md](./harvest-tmc-link.md).

Отдельный учёт культур для KPI (раздел «Отгрузки урожая», таблица `shipments`) сюда не входит —
см. [shipments.md](./shipments.md).

## Harvest‑кейсы

1. **Позиция** категории `harvest` с `crop_code` на складе (после сбора с поля или прихода).
2. **Заявка** на эту позицию — обычная форма; `kind=harvest` ставится сам.
3. **Complete** списывает склад. Запись в `shipments` **не** создаётся.
4. Для KPI менеджер отдельно заводит «Отгрузки урожая» и может привязать эту заявку
   (`shipment_request_id`). См. [harvest-tmc-link.md](./harvest-tmc-link.md).
5. В карточке заявки (`/shipment-requests/{id}`) — блок «Доход по урожаю» по связанным
   `shipments` или кнопка создать отгрузку с prefill.
6. Фильтр списка `?kind=harvest` и колонка «Категория» помогают найти урожайные заявки.
7. Excel и виджет дашборда учитывают harvest наравне с остальными (без исключения по `kind`).

## Связь с модулем «Отгрузки»

- Выполненная заявка **не** создаёт запись в `shipments` (урожай).
- Факт склада — только `inventory_operations` + `shipment_requests.inventory_operation_id`.
- В UI «Отгрузки урожая» внизу страницы — read-only блок только по `kind=inventory`
  (материалы), без влияния на KPI урожая.

## Назначение

- Руководитель создаёт заявку: контрагент, ТМЦ (включая категорию `harvest`), количество, цена, плановая дата, срочность.
- Отдельного типа «заявка на урожай» нет: это та же заявка, `kind` выставляется из категории позиции.
- Исполнитель берёт заявку в работу и завершает её.
- При **выполнении** система создаёт одну складскую операцию расхода (`inventory_operations`, `purpose=shipment_request`).
- До выполнения остаток ТМЦ **не** меняется.
- Виджет дашборда `shipment_requests_summary` и Excel «Заявки на отгрузку» учитывают harvest наравне с остальными (без фильтра по `kind`).

## Feature-flag

В `Organization.settings` (JSONB):

```json
{ "shipment_requests_enabled": true }
```

- Ключ отсутствует → модуль **включён** (обратная совместимость).
- `false` → API `/api/shipment-requests*` отвечает 403, права `shipment_requests.*` снимаются из effective permissions, пункты меню скрыты.
- Переключатель: **Настройки → Часовой пояс** (админ организации).

## Роли и права

| Действие | Право |
|----------|--------|
| Создавать / править / отменять / назначать | `shipment_requests.manage` |
| Список «мои», start / complete | `shipment_requests.execute` |

У менеджера по умолчанию оба права.  
Секция `shipments` подразумевает `shipment_requests.execute` для исполнителя.

## Жизненный цикл

`new` → `in_progress` (start) → `done` (complete)  
либо `new` / `in_progress` → `cancelled` (без операции склада).

- Недостаток остатка на complete → HTTP 400, статус не меняется.
- Повторное complete при уже созданной операции → 409.

## Связь со складом

- FK `shipment_requests.inventory_operation_id` → `inventory_operations.id`.
- Таблицы склада не расширялись под заявки.

## Связь со сменой

При complete, если у исполнителя есть **открытая** смена, в заявку пишется `shift_id`.  
Смена **не** обязательна: без открытой смены `shift_id` остаётся `null`, выполнениека всё равно выполняется.

## Отчёты и дашборд

- Дашборд: виджет «Заявки на отгрузку» (сегодня / ближайшие дни / просрочено / срочные).
- Excel: **Отчёты → Заявки на отгрузку** (`POST /api/reports/shipment-requests`).

## Ограничения

- Только ТМЦ; без отдельного учёта культур и без интеграции с бухгалтерией/эквайрингом.
- UI и API мультитенантны: заявки только своей организации.
