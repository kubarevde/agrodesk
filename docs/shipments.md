# Отгрузки урожая (модуль «Отгрузки»)

## Целевая концепция (ADR)

В АгроДеск есть **два разных контура**, которые нельзя смешивать в одном учёте:

| | **Отгрузки урожая** (`/shipments`, таблица `shipments`) | **Заявки на отгрузку** (`/shipment-requests`) |
|--|--|--|
| Предмет | Урожай / культура | Позиция склада (ТМЦ или урожай-как-товар) |
| Единицы | кг, цена/кг | ед. ТМЦ, цена за ед. |
| Факт | Запись в `shipments` | `inventory_operations` (expense, `purpose=shipment_request`) |
| Склад | **Не** трогает | Списание только при `complete` |
| Роль модуля | Управленческий учёт реализации урожая, KPI, прогноз | Операционный наряд складу / исполнителю |

### Источник данных модуля «Отгрузки урожая»

Модуль построен **исключительно** на таблице `shipments` и **не** использует
`inventory_operations` (ни топливо, ни удобрения, ни урожай-на-складе) для расчёта
культур/кг, графиков, отчёта Excel «Отгрузки» и прогноза.

Фильтр периода на странице `/shipments` (локальный state `from`/`to`, по умолчанию
текущий календарный месяц) передаётся в `GET /api/shipments?from_date=&to_date=`
по полю **`shipments.date`** (хозяйственная дата отгрузки, inclusive). Тот же
отфильтрованный набор питает summary-карточки («Всего отгружено» / «Выручка» /
«Кол-во рейсов»), график, таблицу и карточки — без отдельного month-only запроса.

Любой расход со склада остаётся в домене склада / заявок и **не** попадает в список
и агрегаты урожая автоматически.

### Почему не объединяем таблицы

- Автосоздание `shipments` из выполненной заявки ТМЦ ломает смысл «культуры/кг» и искажает дашборд/прогноз.
- Создание `inventory_operations` из crop-отгрузки выдумало бы складской учёт урожая там, где его нет.
- Двойной учёт одного физического события запрещён условиями продукта.

### Как связаны модули

1. **Данные не дублируются** — разные таблицы, разные отчёты Excel.
2. **UX**: внизу страницы «Отгрузки урожая» — отдельный read-only блок
   «Отгрузки ТМЦ по заявкам» (`kind=inventory` only), без влияния на KPI урожая.
3. **Права**: секция `shipments` — урожай; `shipment_requests.*` — заявки.
4. **Отчёты**:
   - «Отгрузки» — только `shipments` (культуры / кг / выручка);
   - «Заявки на отгрузку» — `shipment_requests` (+ склад при complete).

### Урожай как номенклатура склада

См. [harvest-tmc-link.md](./harvest-tmc-link.md): категория ТМЦ `harvest`, заявки
`kind=harvest` списывают **только** склад; KPI по культурам остаются на `shipments`.

### Harvest‑кейсы в этом модуле

1. **Со склада:** после complete harvest‑заявки создайте запись отгрузки и (по желанию)
   привяжите заявку в поле «Заявка». Остаток уже списан заявкой; эта запись — доход/KPI.
2. **Мимо склада:** только `shipments` без `shipment_request_id` — без складского расхода.
3. В списке отгрузок у связанных записей — ссылка «по заявке #…» на карточку заявки.
4. Блок внизу страницы («Отгрузки ТМЦ по заявкам») показывает только `kind=inventory`
   и **не** входит в KPI урожая.

### Единый ключ культуры (`crop_code`)

Справочник: `org_dictionaries` (`type=crop`, `code` + `name`).

| Сущность | Display (legacy) | Preferred key |
|----------|------------------|---------------|
| Поле `locations` | `crop_type` (имя) | `crop_code` |
| Отгрузка `shipments` | `crop_type` (имя) | `crop_code` |
| Склад harvest SKU | — | `inventory_items.crop_code` |

Новые записи полей/отгрузок пишут оба поля синхронно. Старые строки backfill'ятся миграцией `035_crop_code_unify` при однозначном name→code.

Подробнее по заявкам: [shipment-requests.md](./shipment-requests.md).
